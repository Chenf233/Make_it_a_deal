# FastAPI 增量开发流程

## 1. 适用场景

用于用户可观察的业务和 FastAPI 应用改动：

- 页面、HTTP API、WebSocket 和流媒体接入。
- 用户、包裹、日志和计数等数据库业务。
- 跨模块调用和业务状态机。
- 数据库与硬件、进程或云端的协作。
- 后台业务任务、取消、重试和恢复。

单纯修改某项能力的内部实现时，使用
[功能模块开发流程](module-development.md)。

## 2. 定义用户可观察结果

开始编码前用几句话回答：

```text
谁触发？
成功后用户看到什么？
数据库发生什么变化？
哪些硬件或外部系统发生变化？
什么情况不算成功？
```

不要求正式工单，但必须先明确成功语义和非目标。

## 3. 画出调用链

用一条短链列出真实参与者，例如：

```text
wheels.html
→ wheel_api
→ WheelArrivalController
→ Motor
→ StationCounterRepository
→ HuaweiIoT
```

调用链用于确认：

- 需要读取哪些资产。
- 哪些模块接口已经存在。
- 状态由谁拥有。
- 哪些步骤只能在 RDK 验证。

不要先读取整个项目再寻找需求落点。

## 4. 判断编排位置

### 可以留在 Router

- 单一 Repository 的简单 CRUD。
- 单一 Service 的状态读取或诊断动作。
- HTTP、WebSocket、MJPEG 等协议转换。
- 没有跨模块顺序、后台任务和补偿的薄逻辑。

### 必须进入 Application

- 数据库加硬件或云端副作用。
- 多模块调用顺序表达业务规则。
- 后台任务、锁、超时、取消或重试。
- 跨请求状态、pending token 或业务会话。
- 幂等、重复请求、部分成功或补偿。
- 需要脱离 HTTP 单独测试的流程。

不要为简单读取创建形式化 Use Case，也不要把复杂流程继续堆进 Router。

## 5. 检查模块能力

Application 只能调用能力接口，不应进入模块内部操作 GPIO、线程或 C stdin。

期望：

```python
await arm.place_parcel("A02")
cabinet.open("A01")
await iot.report_station("A", value)
```

不期望：

```python
motor1_half_turn(...)
GPIO.output(...)
iot._process.stdin.write(...)
```

如果缺少合适能力，暂停业务实现，先按模块开发流程补齐接口，再返回当前流程。

## 6. 确定状态所有权

逐项确认权威拥有者，避免同一状态被 Router、Service、数据库和页面同时维护。

常见归属：

| 状态 | 所有者 |
| --- | --- |
| 用户、包裹、日志、持久化计数 | SQLite / Application |
| 物理动作和设备内部状态 | 对应 Service |
| 后台业务任务和跨请求业务状态 | Application |
| 连接、子进程和传输队列 | 对应集成 Service |
| 页面临时交互状态 | Browser |

新增状态时说明是否需要重启恢复；需要恢复的业务状态原则上不得只存在于 Router
模块全局变量中。

## 7. 设计副作用顺序

数据库、硬件和云端无法组成同一个 ACID 事务。实现前必须明确：

- 哪一步是业务成功点。
- 先操作数据库还是先操作外部系统。
- 后续失败是否回滚、补偿或最终一致。
- 重启后如何恢复。
- 哪些失败只记录状态，哪些必须返回业务失败。

示例：成功到站后先原子增加 SQLite 计数，再上报最新绝对值。IoT 失败不回滚本地
计数，因为 SQLite 是真源，重连后可以重发当前值。

## 8. 实现和依赖组装

- Router 负责请求和响应映射。
- Application 使用显式依赖，不新增隐藏全局依赖。
- Repository 负责 SQL 和原子数据库操作。
- Service 负责能力执行。
- `main.py` 构造长期对象并管理生命周期。

不强制所有工作流使用类：

- 无状态流程可以是函数。
- 拥有任务、锁、队列或跨请求状态时使用控制器类。
- 只有需要 Fake、多实现或隔离平台时才定义最小 `Protocol`。

## 9. 本地集成验证

优先组合：

```text
真实 Router 或 Application
临时/隔离 SQLite
Fake Hardware
Dummy Camera
Fake Huawei IoT
```

验证：

- HTTP 输入输出和错误映射。
- Application 调用顺序。
- 数据库最终状态。
- 中断、超时和重复请求。
- 外部能力失败。
- 后台任务取消和关闭。
- 不应发生的硬件、数据库或云端调用。

本地测试重点证明业务编排正确，而不是证明真实设备行为。

## 10. RDK 验证准备

同步 GitHub 前准备：

- 确定的测试命令。
- 环境变量、依赖和配置前置条件。
- 是否需要停止完整 SmartStation。
- 是否会移动硬件或修改真实数据库。
- 成功标准和失败诊断。
- 安全停止和清理方式。

尽量让 RDK 测试验证“真实适配器与平台”，而不是首次发现基础业务错误。

## 11. 旧流程迁移

修改旧复杂流程时采用“触碰迁移”：

- 小型字段、文案或直接调用修改不触发重构。
- 新增副作用、后台任务、恢复策略或显著改变顺序时，考虑抽入 Application。
- 首次迁移先用测试固定原行为。
- 默认保持 API、Schema、GPIO、时序和 IPC 不变。
- 不把无关结构清理混入同一批设备验证。

## 12. 完成状态

按以下层级报告：

1. 业务设计完成。
2. 本地集成完成。
3. RDK 组件验证完成。
4. RDK 端到端完成。

设备不可访问时，应明确写成：

```text
业务实现和本地集成完成；
RDK 验证入口已准备；
等待设备同步验证。
```
